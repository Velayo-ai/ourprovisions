## Secrets & Credentials *(established 2026-08-09 — Bitwarden; supersedes the Google Drive interim)*

### Credential tiers

- **Public by construction** — `REACT_APP_SUPABASE_URL`, the Supabase anon/publishable key, Clerk `pk_`. These ship in the browser bundle; hiding them is not a control. **RLS is the actual lock.**
  > ⚠️ Which makes the **disabled RLS on `provision_cycles`, `shopping_sessions`, `known_stores`** a *live correctness gap in that claim* — not a separate hygiene item. The tier only holds while RLS holds.
- **Genuinely secret** — `service_role`, the Postgres connection string, `SUPABASE_ACCESS_TOKEN`, the Clerk secret key, the Vercel token, agent GitHub PATs, the Splunk ingest token.

`.env.local` contains **only** Tier-public values. It was never the reason a secrets manager mattered — **the agent roster introduces the first Tier-1 credentials into the system at all.**

### Secret distribution model

- **Humans** → Bitwarden **personal vault**, interactive unlock.
- **Agents** → Velayo org → **Secrets Manager** → *one machine account per seat* → project-scoped access token → **`bws run` injects into a subprocess, never to disk.**

The split exists because Password Manager unlock requires the master password, and handing an agent the master password hands it the entire vault with no scoping and no granular revocation. The `BWS_ACCESS_TOKEN` itself still lives on the machine — the bootstrap problem is **bounded and revocable, not eliminated.**

**Distribution mechanism is a correctness property, not only a security one.** The Preview whitespace corruption and the un-propagated Clerk key were both copy-paste failures. Values moved by `bws run` don't acquire invisible characters or miss a rollout.

### Vercel environment ownership

Production and Preview are **Vercel-owned, build-time** — Vercel needs them at build, and there is no Bitwarden→Vercel sync for a one-app fleet. **Development is intentionally empty**: `vercel env pull` returning nothing is designed behaviour.

Chosen as *delete, not repoint* — with Bitwarden as the dev credential source, repointing creates two sources of truth that drift silently. An empty pull fails loudly; a stale-but-plausible file fails six weeks later and looks like a code bug. Note the Vercel CLI is **not installed** on the Surface or the lake desktop, so the documented pull path was never live — a defused latent hazard, not an active leak.

### Auth Pattern
Clerk is configured as a Third-Party Auth provider in Supabase via JWKS endpoint. JWT uses RS256 (not HS256). All Supabase calls include explicit `apikey` + `Authorization` headers. `SECURITY DEFINER` functions required for RLS helpers that call `auth.jwt()`. `bootstrap_new_user` RPC handles new user onboarding atomically — **canonical signature is 3-arg `(p_email, p_invite_code, p_full_name)`; identity is derived server-side from `auth.jwt()->>'sub'` and is NOT a parameter** *(migrations `036`/`037`, dev + prod 2026-08-17 — Authorization Part 2)*. **Exactly one overload exists in both environments**; the four-overload ambiguity is gone.

> **Two claims corrected here 2026-08-17, both disproved by direct observation:**
> **(1)** The old text said the canonical signature was the 4-arg `(p_clerk_id, …)` and that "prod has additional overloads (ambiguity risk)". Both were true when written and are now closed — see above.
> **(2)** The old text said **"Legacy anon key format required."** The deployed prod bundle ships a modern **`sb_publishable_…`** key, and an anon `GET /rest/v1/catalog_items` with it returns `200`. The legacy-JWT requirement no longer holds. ⚠️ **Header gotcha:** these keys do **not** want `Authorization: Bearer <key>` on a direct PostgREST RPC call — doing so returns a bare `Invalid API key` that reads like an authorization result but is a request-shape error. Send `apikey` alone, and control-test with an unrelated `GET` before trusting any negative result.

**Prod auth topology *(provisioned 2026-07-24; DNS-gated cutover pending)*:** The live app `ourprovisions.velayo.ai` (Vercel) → prod Clerk instance hosted at `clerk.ourprovisions.velayo.ai` (**secondary-application** pattern) → prod Supabase `parpauldmbetptkmdwbd` via Third-Party Auth (the **JWKS/issuer must point at the PROD Clerk instance**). The prior — and defective — state was app → **dev** Clerk (`many-puma-34.clerk.accounts.dev`), i.e. prod data behind dev auth. Re-pointing the prod Supabase Third-Party Auth integration to the prod Clerk issuer/JWKS is the **auth kill-switch**: a wrong issuer denies every authenticated query for every user (reversible by re-pointing back). The Clerk publishable key must be **env-driven** (`REACT_APP_CLERK_PUBLISHABLE_KEY`), never a hardcoded `pk_test_` literal in `src/index.js`.

**Fleet auth pattern:** each vessel gets its own secondary Clerk app at `clerk.{app}.velayo.ai`; `clerk.velayo.ai` (the parent-domain primary slot) is **reserved** for a future Velayo-wide / Harbour identity layer, so the first app doesn't mis-claim the company domain. First application of the shared-house / separate-front-door principle to auth.

**Sub-continuity constraint (load-bearing for the dev→prod user migration):** prod `household_members.user_id` is the internal `users.id` (uuid); the Clerk `sub` lives in `users.clerk_id`. Household membership keys on stable internal ids, but each user row still binds to its Clerk `sub` via `clerk_id`. A migration MUST preserve or reconcile `clerk_id` per user, or a migrated user signs in successfully to an **empty app while their real households orphan** — the highest-risk verification of the cutover. (Roster: 10 migrate / 11 drop, settled from a live prod census 2026-07-24.)

**DNS for a Clerk custom domain on Cloudflare must be grey-cloud (DNS-only), never proxied** — proxying loops TLS validation (same lesson as the `.app` landing-page setup).

**Clerk publishable key is env-driven with a fail-loud guard** *(2026-07-25, `a652a52`; `src/index.js`)*. The key comes from `process.env.REACT_APP_CLERK_PUBLISHABLE_KEY` (was a hardcoded `pk_test_` literal that baked dev keys into every bundle). The guard fires a "Configuration error" screen when the key is **falsy** (empty/undefined) — a missing key would otherwise mount `ClerkProvider` with `undefined` and blank the app. **It checks non-empty, NOT validity** — so production safety depends on the Production env holding a non-empty key *that also matches the Supabase-configured issuer*. **Vercel Production env is `pk_live_` as of the 2026-08-15 cutover** (was `pk_test_`, deliberately, for the three weeks the flip was gated). CRA embeds `REACT_APP_*` at build time, so the value is whatever the Vercel scope held at build.

**Vercel `REACT_APP_*` values are inlined at build time — saving the env var changes nothing on the running deployment** *(2026-08-15)*. A redeploy is required, and **"Use existing Build Cache" must be unchecked** or the old key ships inside the new build. Related input hazard: pasting a second value into the field creates **one multi-line value, not two rows** — the same defect class as the 2026-08-09 whitespace/return corruption on the Preview key.

**Verifying which Clerk instance a deployment actually serves: decode the key, don't grep the prefix** *(2026-08-15)*. The Clerk SDK ships **both** prefixes as string constants (`const rf="pk_live_",nf="pk_test_"`), so a bare `pk_test_` appears in a correctly-cut-over production bundle. A grep for the prefix alone reports a false failure. Match the key **with its payload** and base64-decode it — the publishable key decodes to the instance domain plus `$`: prod `pk_live_…` → `clerk.ourprovisions.velayo.ai$`, dev `pk_test_…` → `many-puma-34.clerk.accounts.dev$`. Diff against a same-build control (the dev preview) to confirm the method before trusting the result. This is an outside-the-app check needing no credentials.

**Prod Clerk is LIVE over TLS** *(2026-07-27)* at issuer `https://clerk.ourprovisions.velayo.ai` (JWKS `/.well-known/jwks.json`, API version `2025-11-10` — **matches dev**, so token/`sub`-claim shape is consistent across the cutover). DNS/SSL wall cleared (5 CNAMEs verified + grey-cloud, SSL issued). **The auth-plane flip COMPLETED 2026-08-15** — verified on three independent accounts.

**Supabase Third-Party Auth supports N simultaneous Clerk connections — so an issuer change is additive, never a swap** *(2026-08-15; the mechanism that made the cutover zero-downtime)*. The domain is **not editable in place**: the UI offers only "Add new Clerk connection" and "Delete integration". But connections **coexist and are honoured concurrently**, so the correct move is **add the new issuer alongside the old, verify, then delete the old** — never delete-then-re-add, which opens a window with no provider configured. This also reduces rollback to "redeploy the previous build", with nothing to re-create under pressure. **Adopt fleet-wide for any future auth-plane move.** ⚠️ Corollary: while both are enabled, **a stale dev-issuer token is still accepted** — the old connection is an open auth surface and must be deleted once the new one is proven. As of 2026-08-15 the dev connection is still enabled, deliberately, as rollback.

**`bootstrap_new_user` upserts on `conflict (clerk_id)`** — architecturally load-bearing for the cutover. It assumes `clerk_id` is correct at login time, so: (a) migration must **reconcile `users.clerk_id` to the prod `sub` BEFORE the auth flip**, and (b) reactive/post-flip reconciliation is unsafe — an un-reconciled user's first prod login hits the **`users.email` unique constraint and throws** (a hard error, not a silent empty app), while reconciled users **self-heal** through the conflict branch. Clerk **cannot transfer users** dev→prod (it mints NEW subs); users are re-created in prod Clerk and reconciled by email. **Join keys:** `users.email` and `users.clerk_id` are both `unique not null`; reconciliation is `update users set clerk_id = <prod sub> where email = …` (or `where id = …` for the Dan Test User row, whose `+testNN` email stem makes the email-join ambiguous). This is **Path A** (see ROADMAP DECISIONS 2026-07-27).

**Fleet identity standard — `externalId = internal `users.id``** *(2026-07-27 decision; not yet built)*. Every NEW vessel sets Clerk's `externalId` to the app's own internal user id from provisioning day, so RLS can key on a Velayo-owned id and identity is never hostage to Clerk's `sub`. OurProvisions stays on Path A (`sub`-keyed) for this cutover and migrates onto `externalId` as a follow-up pilot — that migration would change the RLS predicate (`auth.jwt()->>'sub'` → an externalId claim), the JWT template, and `bootstrap_new_user`'s conflict key. This `externalId` seam is what a future **Harbour Identity + fleet-payments** layer attaches to.

#### `household_members`
Join table. Realtime enabled.
- `id`, `household_id`, `user_id`, `role` (owner/member), `joined_at`, `deleted_at`
- **Role model:** `owner` = creator (the un-removable anchor); any member can rename household, remove any non-owner member (incl. self = leave). Owner cannot be removed by anyone and cannot leave — must delete the household to exit. All list actions are shared. No succession in phase 1 — owner exit is delete-only. No co-owners.
- **Membership authorization rule:** "You may soft-delete any membership row in a household you belong to, as long as that row's `role` is not `'owner'`." Leave = the self case; owner-protection falls out for free. No separate is_owner_of helper needed — guard reads the TARGET row's role inline.
- **Soft-delete + revive invariant:** Leaving sets `deleted_at = now()`. Re-join MUST revive (ON CONFLICT DO UPDATE SET deleted_at = null, role = 'member'), never plain INSERT — the leftover soft-deleted row collides with UNIQUE(household_id, user_id). Migration 011 covers the manual invite path; migration 012 covers the URL-invite `bootstrap_new_user` path. BOTH paths must be maintained independently.
- **Re-scoping risk (multi-household):** `useProvisions` + realtime subscriptions must tear down and re-subscribe to the new `household_id` on switch, or stale realtime updates leak from the old household. Inspect before coding the switcher.
- **Timestamp column naming (grep note):** join time **is** recorded — the column is named **`joined_at`**, NOT `created_at`. A grep for `created_at` on this table will come up empty; that is a naming choice, not a missing column. (Corrects a 2026-07-01 handoff that inferred join time wasn't recorded.)
- **Ordering:** `joined_at` is the timestamp column (not `created_at`). `get_current_household_id()` orders `DESC` (newest); `get_my_households()` orders `ASC` (oldest = context default); `bootstrap_new_user` step 3 orders **`hm.joined_at DESC`** (most-recently-joined wins) over a `households`-liveness join. ~~⚠️ **has NO `ORDER BY` on prod — the 002 stopgap is not in the live body** *(verified 2026-07-30)*~~ — **CORRECTED 2026-08-17:** that was true on 2026-07-30 and had already been fixed by a later rewrite before tonight. Read directly from the live function body on **both** databases (byte-identical, `md5 54518e04f054bbbcfb76b9fcf66dac8b`), which carries the ordered, liveness-joined lookup; `036` preserves it verbatim. See three-way ordering bug in Known Debt.

> ⚠️ **Known caveat, carried forward deliberately:** the invite-revive branch and `join_household` reset `deleted_at` but **not** `joined_at`, so a user who left and rejoined sorts by their *original* join time. #### `household_staples` *(migration 016, live dev+prod 2026-07-07)*
Per-household staple preferences. **Row-presence = stapled** — the single source of truth for staple state, for BOTH global and custom catalog items (replaces the dormant `catalog_items.is_staple` boolean).
- `id` uuid PK, `household_id` uuid NOT NULL → `households(id)` `ON DELETE CASCADE`, `catalog_item_id` uuid NOT NULL → `catalog_items(id)` `ON DELETE CASCADE`, `created_at`.
- `UNIQUE (household_id, catalog_item_id)` — one staple row per (household, item); insert = staple, delete = unstaple; no UPDATE path.
- **RLS:** `select` / `insert` / `delete` all gated on `is_member_of(household_id)`. No UPDATE policy (row-presence model).
- **FK carve-out (deliberate):** `catalog_item_id` is `ON DELETE CASCADE`, a **scoped exception** to the "all FKs referencing `catalog_items` are `NO ACTION`" invariant below. ### Foreign Key Constraints — ALL `NO ACTION` (verified June 8; `users` map added 2026-08-15)

**`users_clerk_id_key` is the second no-partial-index trap** *(2026-08-15)*. `public.users` carries exactly three constraints: `users_pkey`, `UNIQUE (email)`, `UNIQUE (clerk_id)`. **Neither unique has a `WHERE deleted_at IS NULL` clause.** The email trap was already known; `clerk_id` has the identical shape and the same consequence. **Any retire, merge, or re-signup path must free *both* values, not just the email** — otherwise a soft-deleted user permanently blocks their own return. This is why a retire mangles rather than deletes, and why the mangle prefixes (`retired-YYYY-MM-DD-<original>`) instead of overwriting: uniqueness holds, the value is freed, and the row stays self-documenting.

**Sixteen FK columns reference `public.users`, and every one is `NO ACTION`** *(2026-08-15, enumerated from `information_schema` — six of them appear on tables no prior spec or census had listed)*. Nothing cascades, nothing nulls:

`catalog_items.created_by` · `household_invites.created_by` · `household_invites.accepted_by` · `household_members.user_id` · `households.created_by` · `known_stores.added_by` · `list_item_contributors.user_id` · `list_items.added_by` · `list_items.checked_by` · `provision_cycles.created_by` · `shopping_sessions.user_id` · `velayo_crew_members.user_id` · `velayo_crew_members.invited_by` · `velayo_crews.created_by` · `waste_events.logged_by`

**Consequence: any `DELETE` on `households` must clear `provision_cycles`, `shopping_sessions` and `known_stores` first, or it throws.** These are the same three tables carrying the RLS-disabled CRITICAL advisories — they keep surfacing because nothing in the schema treats them as first-class. **Never enumerate a teardown surface from a cached column inventory** (`Supabase_Snippet_Public_Schema_Column_Inventory.csv` covers 11 tables, is missing at least six live ones, and produced a query against a column that does not exist). Ask `information_schema` — it is authoritative and reports delete rules too.

**`user_hidden_items` has no foreign key to `users`.** It keys on `clerk_id` (**text**), so it does not appear in the FK map above, is invisible to any teardown derived from it, and is **stranded by the mangle** — its rows end up pointing at a string that resolves to nobody. Harmless in practice today; a real orphan class. Same class as the `users_email_key` finding: **a column that means something the schema does not enforce.**

**`velayo_crews` / `velayo_crew_members` exist in prod** and reference `users`, but nothing in ROADMAP or ARCHITECTURE says the Harbour identity layer has live tables. Reconcile before the fleet-identity session.

Every FK referencing `catalog_items` (and the list/contributor chain) is `delete_rule = NO ACTION`:
- `list_items.catalog_item_id`, `list_items.household_id`, `list_items.added_by`, `list_items.checked_by`, `list_items.cycle_id`, `list_items.rolled_from_item_id`
- `waste_events.catalog_item_id`
- `user_hidden_items.catalog_item_id`
- `list_item_contributors.list_item_id`, `list_item_contributors.user_id`

**Design implication:** Postgres will *block* deletion of any referenced row (no cascade, no set-null). This protects against silently orphaning list data — but means the **Delete feature cannot be a simple `delete`**. Deleting a custom catalog item requires a multi-step SECURITY DEFINER RPC that handles references first (or soft-deletes the row via `deleted_at`, keeping FKs valid and history intact). See `SPEC_hide_delete.md`.

**Scoped exception (2026-07-07):** `household_staples.catalog_item_id` is `ON DELETE CASCADE`, NOT `NO ACTION`. Deliberate — staples are disposable *preference* rows, not history, so they should vanish with a deleted custom item rather than blocking its deletion. This is the only intentional deviation from the rule; every other `catalog_items` FK remains `NO ACTION`. Do not "normalize" it back.

#### `category_avg_prices`
Aggregates `round(avg(price_hint), 2)` per category across **global seed `catalog_items`** (`is_global = true`, `price_hint IS NOT NULL`, `deleted_at IS NULL`). ### Meal ↔ item / quantity / servings
- A meal placed on the plan has a `servings` value (defaults from the recipe base; may default from an Event's headcount when Events lands).
- Each recipe ingredient stores a **per-serving amount** (stable — this is "the recipe").
- A list item's quantity = per-serving amount × meal servings, **UNLESS a user override exists**, in which case the override wins and persists through re-scaling (sticky exceptions the servings dial does not stomp).
- **"Have it" = a per-item override to 0.** Swipe-left (Meals lens) and stepper-to-zero (Ingredients lens) are two gestures for the SAME override write.
- Meal-added list items carry an **origin link** (which meal), surfaced as a tag ("from Lemon pasta") — load-bearing for the "why is this on my list?" reconcile flow.

### One-list / two-lens sync invariant
- There is **ONE list** (`list_items`) as source of truth.
- **Ingredients lens** = the list shown flat; **Meals lens** = the same list grouped by meal origin. Lenses are viewing angles, not separate data.
- An edit through either lens (Dan zeros spaghetti in Ingredients; Helen swipes mozzarella in Meals) is the **same write** and must sync in realtime across lenses (Supabase realtime is already on `list_items`).
- Both gestures must produce the SAME state (quantity 0, still visible, still tagged) so the two lenses never diverge. Same shape as the existing **"hide is a lens, not an edit"** principle — the recipe is stable; only the shopping instance changes.

#### Create-meal — designed 2026-08-19, NOT built *(mockup: `docs/mockups/mockup_create_meal.html`)*
- **Create-meal is a client-side STAGING flow, not a write-per-action form.** Name and ingredients accumulate in local component state; **nothing touches `meals`/`meal_ingredients` until "Save Meal" commits.** Same shape as the household Edit sheet's roster pattern — build up, one commit — not a series of per-ingredient RPC calls.
- **New-item creation inside the meal-builder is NOT new backend surface.** It calls the existing `insert_custom_catalog_item` (idempotent, normalized-name reuse, migration 018). The "add an ingredient not in the catalog" path and Browse's own "no results" path are **the same mechanism, not two implementations free to drift.** *A meal ingredient is a catalog item* — the load-bearing 2026-07-29 FK decision — now holds at the **UI layer**, not only in the schema.
- ⚠️ **CROSS-CUTTING — THE TWO-LEDGER PAIR.** `list_item_meals` (meal provenance) and `list_item_contributors` (user provenance) are **independent ledgers on the same `list_items` row**. They must **never** be merged in data — writing a contributor row from the meal-add path would conflate "a person put this here" with "a meal put this here" and corrupt the user ledger exactly as the missing quantity corrupted the count. **They reconcile ONLY in the SHOP display rule** (clay "Added by" facet, then teal "For {meal}" facet; teal appears **iff** a meal is involved). Any future work touching either ledger must treat them as a known pair — quantity, display and sync each broke separately until all three were fixed against this one model.
- **CROSS-CUTTING — MEAL SURFACES POLL WHILE VISIBLE, NEVER UNCONDITIONALLY.** Both meal-fed surfaces refresh on the 2s poll **only while their surface is the visible tab**: SHOP refreshes provenance only on a tick where a list fingerprint (`id:quantity` pairs) actually moved, and PLAN's meals interval exists only while PLAN is open. A passive viewer stays in sync without navigating; **an idle client issues neither query.** The naive fix — refetch every tick — is the query multiplier the original "Cheap read; no poll" note was avoiding. The two need **separate** triggers: editing a meal touches `meals`/`meal_ingredients` without touching `list_items`, so the SHOP list-change signal structurally cannot see it.
- ✅ **`list_item_meals` NOW RECORDS QUANTITY — resolved 2026-08-20 by migration `039` (`quantity_contributed`), taking option (a).** It previously recorded *that* a meal contributed, never *how much*, which is why removal stayed out of v1. The gap surfaced concretely during `deleteMeal` verification: two meals each contributing 1 of one item merged to `×2`, and deleting one left `×2` because no amount existed to subtract. `add_meal_to_list` now writes the amount **additively**, mirroring the `list_items.quantity` increment so the two cannot drift. **Legacy rows default to 0 and are inert** — delete drops only their provenance link and leaves quantity alone, degrading to pre-`039` behavior rather than zeroing without basis. ⚠️ **The reconciliation caveat REMAINS OPEN:** the plain manual stepper is still meal-unaware by design, so the governing test — two members independently decrementing one shared ingredient that two meals both contributed to — is **not** solved by `039`.
- **PRINCIPLE — a naming problem that resists every candidate verb is usually a structural gap.** "Add all" / "Add to Shop" were attempts to name a destination PLAN cannot yet express; the copy only resolves once the Day/Time/Occasion layer exists ("Add to Tuesday"). **Reach for the structure, not the thesaurus.**
- ⚠️ **MEALS ARE CREATE-ONLY AT BOTH LAYERS — no edit, no delete** *(found 2026-08-19)*. `useProvisions.js` exports only `fetchMeals`, `createMeal`, `addMealToList`, `fetchMealProvenance`; **there is no `updateMeal` or `deleteMeal`**, so the gap is not merely an unwired UI the way `createMeal` was. Once created, a meal is permanent short of raw SQL.
- ✅ **`fetchMealProvenance` NOW FILTERS `meals.deleted_at` — FIXED 2026-08-20 (`5765ad4`), in the same commit that shipped delete.** It was a live latent defect that a delete feature would have activated: the join filtered only `list_items.deleted_at`, and **`list_item_meals.meal_id`'s `on delete cascade` fires on HARD delete only**, so a soft-delete left every provenance row live and the SHOP badge would have kept naming a deleted meal — the same shape as the 2026-07-30 phantom-meal-badge defect. **The standing rule stands and this is its proof case: when rows are soft-deleted, EVERY read path must filter `deleted_at IS NULL`.** The filter is load-bearing and marked as such in the source; removing it silently resurrects phantom badges.
- **Editing a meal does NOT retroactively change list items already added from it** — `add_meal_to_list` folds quantities at add time. This is **consistent with *"the recipe is stable; only the shopping instance changes"***, but today it is true as a side effect rather than as a decision; recorded so the EDIT surface is designed around it deliberately.
- **PRINCIPLE — mock against the running app, not against memory of it.** Every iteration checked against live screenshots caught real drift, and two invented steps (a redundant "Create & Add" confirm; results shown against an empty query) were removed only because the real behaviour was looked at.

#### As built — create / edit meal *(2026-08-20, `0fd9c39`→`ab4546a`; **dev only**)*
- **One parameterized `MealSheet` (`mode: create | edit`)**, built as a single component from the start rather than retrofitting edit onto a create-only sheet. The draft lives entirely in local state; nothing touches `meals`/`meal_ingredients` until Save.
- **`updateMeal`** mirrors `createMeal`'s plain-write shape — update the `meals` row, then **blanket soft-delete every live `meal_ingredients` row and reinsert the draft**. Deliberately not an RPC: edit is household-owned, RLS-protected, and carries none of the cross-cutting concerns (advisory lock, cycle resolution) that justify `add_meal_to_list`'s SECURITY DEFINER shape. **Blanket replace is safe because `meal_ingredients.id` is referenced by nothing** — `list_item_meals` keys on `meal_id` — and verified against the live DB: the only unique index is the pkey, so reinserting the same `catalog_item_id` after a soft-delete cannot conflict.
- **`createCatalogItem`** added — creates a catalog row **and nothing else**. The only prior path to `insert_custom_catalog_item` is inside `updateQty`, which also writes a `list_items` row; reusing it would have put every new meal ingredient straight onto the household's shopping list. Mirrors `updateQty`'s hidden-item resolver so a hidden ingredient resolves rather than forking a duplicate.
- **A meal needs only a name.** `canSave` no longer requires an ingredient in either mode — the old asymmetry made an empty meal unreachable by creating one yet reachable by emptying one.

#### `SwipeToRemove` is now a general N-action wrapper *(2026-08-20)*
- Renders **only the buttons whose handlers are passed** (Edit / Staple / Hide, or any subset). Reveal width scales at **80px per action**.
- ⚠️ **Width counts HANDLERS PASSED, not buttons rendered — and the distinction is load-bearing.** `canEdit` is false for global seed rows when prices are hidden, so counting rendered buttons would shrink those panels 240→160 and silently alter a surface no such change intended to touch. Every catalog call site passes three handlers and stays at exactly 240.
- **PRINCIPLE — a threshold tuned against a fixed dimension becomes a bug the moment that dimension varies.** `SWIPE_THRESHOLD`'s flat 60px was a quarter of a 240px panel and **three quarters of an 80px one**, so short drags hit the snap-back branch and the row read as stuck while actually **re-opening correctly**. Now `min(SWIPE_THRESHOLD, REVEAL_WIDTH / 3)`, scoped to the edit branch only — the swipe-to-remove path keeps its 60px, because lowering the bar on an irreversible action is a different risk entirely.
- ⚠️ **PRINCIPLE — gesture logic must read a ref, never batched state.** `move` events are **continuous priority** in React 18, so their `setOffsetX` updates are scheduled rather than flushed; a discrete `mouseup` can run before the last move commits. The old code computed `delta` from stale state against a live ref, then `handleStart` seeded the next gesture's baseline from the bad result — **compounding until it wedged, and clearing whenever an unrelated re-render flushed the backlog.** `offsetXRef` is now written in lockstep with every `setOffsetX`; state is retained purely for rendering. Latent on wide panels, exposed by the narrow one.

#### Meal planning v1 — designed and spec'd, NOT built *(2026-08-20; `docs/specs/active/SPEC_meal_planning_v1.md`)*

- **`removeMealFromList(mealId)`** — the counterpart to `addMealToList`. Zeros each ingredient through the existing `updateQty` path so unshared items leave and shared items still needed by another meal stay, which is the verified reverse of the merge behaviour. **Open at build time:** client loop vs. new RPC; prefer the loop if it reproduces reverse-merge correctly.
- **Arrangement is shared and needs persistence** — a `sort_order`/position whose home (on `meals` vs. a light new table) is an open build-time decision.
- **v2 will likely need a real `plan_occasions`-style table** for days, undated/recurring meals and divergence. **v1 deliberately avoids one**, because derived-active carries it without schema.
- ✅ **Shared-ingredient quantity accounting — NO LONGER DEFERRED; landed 2026-08-20 via `039`.** `list_item_meals.quantity_contributed` gives removal an exact per-meal amount, so `deleteMeal` decrements precisely instead of the old all-or-nothing branch. The Dan/Helen bread scenario resolves for the delete path. ⚠️ **Still unsolved:** the manual stepper remains meal-unaware, so a member hand-decrementing a shared ingredient still moves a quantity two meals are counting on.

### Consumption signal (strategic frame — informs schema priorities)
- The defensible asset is the household's **live consumption signal**, not the list. Two sensors feed it: **list** (intention: what was wanted) + **receipts** (ground truth: what was bought); the gap = impulse (bought-not-listed) + forgot (listed-not-bought).
- The meal-reconcile "have it" gesture is itself a **low-friction pantry sensor** — worth preserving that byproduct.
- Provisions/inventory tracking is **opt-in on the slow-moving tail only**; velocity is inferred from list history, not user-entered.

### Meals data model — buildable schema *(designed 2026-07-28, NOT yet migrated; `SPEC_meals_model.md` + `SPEC_meal_sharing.md`)*

**New tables** (all household-scoped RLS via `auth.jwt()->>'sub'`, **NEVER `auth.uid()`**; a **live RLS test** is required post-merge — the SQL editor bypasses RLS, only the running app proves policies):
- **`meals`** — household-owned (`household_id`); `base_servings` (scaling seam, = 1 today); `created_by` (**preserves the original author across a copy** — `created_by` = who first created it, `household_id` = who owns this version); soft-delete. `photo_url` deferred (generalizes from OurBanner).
- **`meal_ingredients`** — join: `meal_id`, **`catalog_item_id` (FK — load-bearing:** this FK is what lets a meal flow into `list_items`); `quantity_per_serving` (a ratio always; `base_servings`=1 makes it read as a flat qty today). No override column yet (the Option-1 seam).
- **`list_item_meals`** — provenance join, PK (`list_item_id`, `meal_id`), plus **`quantity_contributed`** (numeric, not null, default 0 — added `039`, 2026-08-20, **dev only; NOT on prod**). Powers the SHOP provenance line's **teal meal facet** (the "Multiple meals" count string was retired 2026-08-20 in favour of named, and-joined meals) and precise remove/delete. FK on `meal_id` gives referential integrity. ⚠️ **No user column** — nothing records *who added this meal to the list*, only `meals.created_by` (the author). That absence is exactly why the meal facet currently carries no name.
- **`meal_shares`** — the giving "doorbell": `meal_id` (source), `from_household_id`, `to_household_id`, `shared_by`, `status` (pending/accepted/declined), `created_at`, `resolved_at`. **Accept-first** — the copy happens at ACCEPT, not at give.

**Lineage columns on the meal COPY** (provenance only, NEVER sync): `copied_from_meal_id`, `copied_from_household_id`, `copied_at`.

**Constraints / patterns:**
- `uq_live_list_item` **unchanged** — one live list row per catalog item per household, upheld by the meal-add path (**increment, don't duplicate**).
- Recommended partial unique index on `meal_shares (meal_id, to_household_id) WHERE status = 'pending'` to block duplicate offers (confirm before build).
- **JOIN table over array column** for meal↔item links — referential integrity on the sacred shared list, no dangling meal refs.

**Cross-cutting principles surfaced:**
- **Two kinds of provenance:** DISPLAYED ATTRIBUTION (editable free text on the copy; may credit people not in the ledger — "Elly and Cassie's meatballs") vs. SHARE HISTORY (immutable transaction record). The name is what the household calls it; the ledger is what happened — **do not validate the name against the ledger** ("don't force things on users").
- **Lineage (breadcrumb on the meal) vs. transaction (`meal_shares` row) are different records** — lineage survives archival of the transaction. Receipt vs. family tree.
- **Copy vs. reference is a product split** — copy (snapshot, drift-OK) = OurProvisions/places; reference (live-sync, evolving) = OurChef/people.
- **Foundational seam:** a household is one instance of a general "context that owns provisioning." `created_by` + lineage keep the people-owned and events futures possible without building them now (see **Context/Events** → ROADMAP NEXT).

## Design Principles

- **★ Layout follows the job, not the component.** *(2026-08-09 — Browse category rail.)* The category pill is **one component with two deliberately divergent layouts**: a horizontally scrolling **rail** (Browse — multi-select, *browsing*) and a wrapped **exhaustive grid** (add-item — single-select, *completing*). **They must not be unified.** The governing rule: **scroll where you're grazing, show everything where you're choosing.** Browse-layer controls may scroll because the user is surveying; a task-completion picker must render every option, because a hidden option at filing time produces misfiled items — and **catalog quality is the long-term asset**. Corollary: **context answers the question where it can** — entering add-item from a section header pre-selects that category, turning the picker from a question into a confirmation.
- **Filter controls keep pill styling; they never adopt tab or underline styling.** *(2026-08-09.)* Pills read as toggles; tabs read as one-of-N navigation. A multi-select control dressed as navigation misrepresents what it does. Related: **no checkmark swap on active multi-select filters** — a row of identical ticks flattens the actives into each other, so the **fill** carries state while the icon keeps each pill identifiable. (Checkmark treatment remains valid for *single*-select.)
- **A vessel owns its own splash; the parent brand signs the footer (the fleet colophon pattern).** *(2026-07-22 — splash-experience design.)* The launch splash shows the **product's** palette and wordmark, with Velayo demoted to a quiet `VELAYO INC.` footer — not a Velayo-branded card. Warm app palette + product wordmark lead + Velayo colophon + a dissolve into the app is the **fleet-wide pattern** every future vessel (OurKeep, OurManifest, OurDiscovery…) inherits. Showing the parent brand at the front door of a specific product is a mismatch.
- **A threshold that lies is worse than no threshold — the launch feeling must carry into the app.** *(2026-07-22.)* The splash cannot be a disconnected flourish. The espresso header retains a faint **permanent BVI depth-glow** (the same water the dissolve washed through), and app interactions (row add, tab switch, count change) share the scene's easing `cubic-bezier(0.16,1,0.3,1)` — "calm competence" carried through the whole app. This atmospheric-header + shared-motion-language expansion is a real scope increase — likely its own fast-follow phase, not the first splash build.
- **Entity/membership grammar — collection → selected → scoped detail.** *(2026-07-18 — household-management redesign.)* A surface that manages a set of entities and the people scoped to one of them has a single shape: the **collection** (CRUD on the entities) above the line; the **selected** entity drives a **scoped detail** zone (its membership) below; one selection updates both, and the detail zone recomputes on selection change (same class as the filter-reset rule). Introduced for household management; **deliberately built to generalize to a future Context entity (households ∪ events) in Phase II** — leave conceptual room for a "Your Events" sibling section without building Event structures now. Migration 024's photo/framing/wordmark columns land on `households` but are really *context* identity; shape the build so a future Context table isn't fought (do NOT re-architect 024 for it).
- **Row-level actions are bare — icon or icon+label, right edge, no container.** *(2026-07-18.)* Formalized across the management sheet: the active row's **Edit pencil** and the member row's **trash** are both containerless glyphs at the right edge. No plate, no pill — selection state and the action's own label carry the meaning. A uniform rule beats "icon-only bare, labeled gets a pill."
- **The app owns the shareable artifact — Invite delegates to `navigator.share()`, holds no in-app share state.** *(2026-07-18, extends the 2026-07-16 principle.)* Invite calls the OS share sheet with a pre-filled message; there is **no in-app share UI and no persistent banner**. The old banner bug (rendered in the main scroll, lingered after sending) is deleted *by construction* — there is no in-app surface to linger, and the banner state machine that carried the defect is removed. "Copy link" goes too (the share sheet offers Copy). Verify the app calls `navigator.share()`, not a self-rendered sheet.
- **★ Judge the live page in the real browser, not a mockup in an in-app viewer.** *(2026-07-17.)* Four rounds were spent "fixing" a dark-mode bug that never existed — Claude's in-app browser was theming a *downloaded* HTML file; `ourprovisions.app` in Safari was correct the whole time. **Confirm which surface you're looking at before debugging the render** — a screenshot of a viewer is not a screenshot of the page. Same family as "truth is a query against the correct environment," extended to what you're looking *through*, not just what you query. The `color-scheme:light` declaration (meta + `:root`) stays as cheap insurance for a one-palette page, but it fixes nothing. *(This strikes the earlier "dark mode was never tested" finding — it was a false alarm.)*
- **Two-confidence separation (systemic AI pattern).** `price_confidence` (extraction — how clearly the number was read) must never be conflated with `match_confidence` (reconcile — how confidently the line maps to a catalog item). Conflation produces a system confidently wrong about the thing it should be humble about. *(Established 2026-07-03 — receipt import design.)*
- **Most "matching" problems are normalization problems.** Normalize (lowercase, strip punctuation, collapse whitespace, alias) before comparing; reach for a fuzzy library only after real data proves deterministic matching is insufficient. KISS. *(Established 2026-07-03.)*
- **Raw data is sacred.** `raw_payload` (receipt header) + `raw_text` (line) kept redundantly so a better parser can reprocess old receipts without data loss. Confirmed `receipt_items` are soft-delete only — they are the future training set. Never hard-delete confirmed receipt lines. *(Established 2026-07-03.)*
- **AI results aligned by stable key, never array position.** When returning AI-parsed arrays (e.g. receipt lines), align results by `raw_text` (the verbatim anchor), not by array index — models reorder and drop elements. **Shaped failures** (`{ ok: true/false, ... }`) from every AI call so the UI branches predictably and never silently drops data. *(Established 2026-07-03.)*
- **`.modal` is the canonical modal card class; `.modal-box` is dead — do not use.** Phantom-class bug found twice (wrap-up modal, Jul 3). Inline `maxWidth` correctly overrides `.modal`'s 420px default. If a third phantom class appears, run a grep-for-orphaned-classnames hygiene pass across `App.js` vs the stylesheet. *(Established 2026-07-03.)*
- **The shared list is sacred.** No per-user view preference (Hide, filter) ever suppresses what the household has put on the shared list. Personalization lives in the view layer; the list is shared truth. *(Established June 8 — the principle behind the per-user-hide fix.)*
- **Hide vs. Delete are different verbs for different scopes.** Hide = personal view preference (any item, per-user, reversible). Delete = household action on ownership (custom items only, household-wide, cascades). Item type (`is_global`) determines which verbs are available. See `SPEC_hide_delete.md`.
- **Evaluate against the user's mental model, not internal correctness (the mismatch pattern).** *(Established 2026-07-14 — Chris & Heddi beta session.)* Nearly every finding that session was a *model mismatch*, not a broken feature: swipe vs. long-press; "Search" label vs. filter behavior; hide-but-can't-find; re-invite people you already know. In every case the code did exactly what it was told and users expected something else. When a design surface confuses users, first ask which mental model it violated — the fix is usually to match the model, not to add UI.
- **Own the data from day one.** No vendor lock-in on the data layer.
- **Capture behavioral signals silently.** Sequence, location, timing — no user configuration.
- **Soft delete everything.** Never hard delete user data.
- **Schema stays ahead of the roadmap.** Add role fields and source fields early; populate later.
- **Prices are infrastructure, not UI.** Manual price entry creates friction. Price data builds passively through receipt scanning.
- **Merge don't duplicate.** When multiple users add the same item, merge with quantity increment + contributor attribution.
- **`window.location.reload()` is an anti-pattern.** Always use `refreshCatalog()` instead.
- **Transient network failures degrade gracefully — never alarm the user.** A blip on marine wifi is not an error. Classify transport failures vs. real HTTP/RLS errors (`classifyFetchError`). Transient → silent pill + keep last-good data. Real → red toast as before. Default to `'real'` when uncertain (fail safe). See `classifyFetchError + ConnectivityPill` pattern.
- **Optimistic writes roll back unconditionally.** On any write failure (transient or real), rollback runs first, then the notification branches. The user always returns to true-server-state. No phantom saves under any error type.
- **Two roles only (owner/member). UI shows capability, not role nouns.** Internal shorthand "captain/crew"; DB stores owner/member; product surfaces a Remove button, not a "Captain" badge. No nautical labels in the product.
- **Activator principle.** The person who creates a space carries no ongoing authority over the group — only the structural responsibility of being the un-removable anchor. Any member can remove any non-creator. Equal authority within the group is foundational to "Our*" products.
- **Attribution is universal; ownership is pinned and rare.** Attribution (who created an item/category/household) is shown freely everywhere. Ownership gates only irreversible, group-affecting actions (delete household) and is pinned to the single creator anchor. Items and categories carry attribution — they carry no ownership anchor.
- **Soft-delete + revive — never re-insert on rejoin.** Leaving sets `household_members.deleted_at = now()`. Re-join must revive via upsert (ON CONFLICT DO UPDATE), never plain INSERT — the leftover soft-deleted row collides with UNIQUE(household_id, user_id). Two join paths exist (`acceptInvite` + URL-invite `bootstrap_new_user`); a fix to one does NOT cover the other. Always use column-target conflict form — constraint names drift between dev and prod.
- **Active context is client-authoritative (the Harbour standard).** Each app instance holds its own active household (React context + localStorage, keyed to the Clerk user); the server authorizes the claimed household, never infers or picks it. `is_member_of` is the authorization primitive; `get_my_households()` is the enumeration authority. `get_current_household_id()`'s "pick a household" role is retired for write paths — replaced by "authorize the claimed household." Generalizes to the fleet (active vessel, active kitchen). *(Established Jun 17.)*
- **Switcher reveals progressively.** No switcher chrome at 1 household. A tappable household-name sub-line appears only at 2+ households. "Create new household" is the act that unlocks it. Zero friction for the common case.

## Key Patterns

### Membership creation is RPC-only — `household_members` has no INSERT policy *(2026-08-17, migration `035`)*
`household_members` carries **exactly one client-facing policy: `household_members_select`** (`is_member_of(household_id)`). There is no INSERT, UPDATE or DELETE policy, and that absence is the design — it states that membership is created only by `SECURITY DEFINER` RPCs (`bootstrap_new_user`, `join_household`) and removed only by soft-delete RPCs. The dropped `household_members_insert` was `WITH CHECK (true)`, i.e. any authenticated caller could self-insert into any household at `role: 'owner'`.

> **Dropping a policy is safe here only because of a fact worth stating explicitly:** a `SECURITY DEFINER` function bypasses RLS **only if its owner is exempt**, and an owner is exempt only when it owns the table **and** the table does not have `FORCE ROW LEVEL SECURITY`. `household_members` is owned by `postgres` with **`relforcerowsecurity = false`**, and every inserting function is owned by `postgres`. **Verify both halves before dropping a policy any RPC depends on** — had FORCE been set, `035` would have locked every user out of joining a household.

### Zero-downtime RPC signature changes — additive migration, client deploy, removal migration *(2026-08-17, migrations `036`/`037`)*
Changing an RPC's *signature* is not like changing its body: the deployed bundle calls the old signature by name and argument set, and PostgREST resolves per-call. Dropping and recreating in one migration makes every in-flight client call return `PGRST202 "Could not find the function"` the instant it lands. For `bootstrap_new_user` that meant **every sign-in**, not just new signups, because bootstrap runs in Effect 1 on each session.

The pattern, run identically per environment:
1. **Additive migration** — create the new signature *alongside* the old one. Nothing breaks; both resolve.
2. **Deploy the client** calling the new signature; verify on the deployed domain.
3. **Removal migration** — drop the old signature. This is the step that actually closes the defect.

> **The intermediate state looks finished and is not.** After step 1 the hardened function exists, so the fix reads as shipped while the old vulnerable signature is still live and still `anon`-executable. Never park between steps 1 and 3 across sessions — that is the shape that produced the `024` and `033` record gaps.
>
> **Ordering inside step 1 can be load-bearing:** the new 3-arg `(text,text,text)` was type-identical to a legacy overload, and Postgres refuses to rename input parameters via `CREATE OR REPLACE` (`ERROR: cannot change name of input parameter`). The legacy DROP had to precede the CREATE in the same transaction.
>
> **`drop function if exists` makes one file portable across environments** that have drifted — prod carried three legacy overloads dev did not, and the same file dropped three real functions on prod while no-opping harmlessly on dev. Prefer this over environment-specific migrations, which create exactly the asymmetry that later reads as an unexplained gap.

### Verifying an identity-forgery fix — the trivially-true check trap *(2026-08-17)*
When a fix removes a client-supplied identity parameter, the obvious check is a bare anon-key call with only the *safe* parameters. **That check is worthless on its own**: it returns `42501` identically before and after, because the hardened function was never granted to `anon` in the first place. Same trap as `033`'s unchanged row count.

The evidence is the **forged shape**: call with the removed parameter (`p_clerk_id`) against a **throwaway identity value that matches no live row**, so the pre-fix path is exercised without mutating a real user. Expect `PGRST202`.

> **Pair it with a control call.** A `PGRST202` alone is ambiguous — it could equally mean the RPC layer is broken. Fire the *identical* forged shape at a still-vulnerable sibling (`create_household`, which still takes `p_clerk_id`): it reached the function body and raised `P0001` from inside, proving the block on `bootstrap_new_user` is **signature-specific**, not a blanket failure.
>
> **None of these checks can be run from the SQL editor** — it connects as `postgres`, owns the objects and bypasses both grants and RLS. It will succeed whether the fix worked or not. Run them from outside the database. Same lesson as `022`, `033` and `035`.

### One descriptor slot, precedence-ordered *(2026-08-09 — Browse; **BUILT 2026-08-10**)*
The Browse descriptor line now has **two producers**: the declutter cycle and the category filters. The governing rule is **replacement, not concatenation** — when `selectedCategories.length > 0` the filter line renders and the cycle line is **suppressed**; otherwise cycle behaviour is untouched. The cycle's own copy is unchanged; only its **precedence** is. Concatenation was rejected as too long for one phone row, and because the filter line already does the cycle line's job better.

Filter copy **names the categories** (`Showing only Produce and Dairy — 25 items`) rather than phrasing a consequence or showing a bare count — names stay meaningful after the rail scrolls out of reach. *(Verb amended 2026-08-10: **`Showing only`, in every phase** — the phase-1 `Filtering` special case is deleted. `Filtering Produce` is backwards, since Produce is what *survives*; and the user's real question is "where did Bacon go", which **`only`** answers in one word. The line's presence already signals that filters are on.)*

> **Any future producer writing to this slot must declare where it sits in that order.** A truth table across all six phase × filter states is in `docs/specs/active/SPEC_browse_category_rail.md`; **row four — phase 1 + filters active shows the filter line** — is the one that catches a wrong precedence.

### Open-set category values — `catalog_items.category` is not an enum *(architectural fact, confirmed 2026-08-09)*
`catalog_items.category` carries **no enum constraint**, and users create values: `Mexican Asian` and `Bread & Desserts` are **live prod evidence**. **Any code keyed on category — icon maps, ordering, grouping — must degrade gracefully on unknown values.** For the Browse rail this means the icon map is a lookup with a **mandatory 📦 fallback**, treated as *design, not defensive padding*: an exhaustive map is a map that breaks on the next user-created category. Recorded here because it will recur.

### Splash / entry scene — resolve-in-place, readiness-gated, wordmark-relative, runtime-measured + hidden-target hand-off *(motion model 2026-07-25 v3, supersedes the 2026-07-23 v2 3-act reveal; `SplashScreen` in `App.js`; per `docs/specs/built/SPEC_splash_resolve_v3.md`)*
The animated splash is the **first mounted React view**, NOT the native launch screen — Apple forbids animating the true launch screen, so on native iOS (1.0) it stays static and the animated scene lives here. It **auto-plays on cold start** — no tap gate (the "Tap to enter" gesture existed only to satisfy audio autoplay, and audio moved to Trip Complete). **v3 (2026-07-25):** the whole lockup **resolves as ONE slow gesture** — a blur→sharp IN PLACE (~2.5s), then a simple surfacing dissolve; this replaced v2's staged 3-act reveal (horizon → vessel → house with beats), which read as a PowerPoint build. Load-bearing facts:
- **Motion = one shared resolve, not staged acts.** Every foreground element (wordmark, arch, tagline, foot) animates the SAME keyframe — `opacity 0→1` + `filter: blur(18px→0)` (satellites ~10px) — on ONE curve `cubic-bezier(0.22,1,0.36,1)`, with a **<120ms internal stagger** so it breathes as one event, never a build. **No translation** (the hand-off exit is the sequence's only travel) and **no self-drawing arch** — the arch renders already-drawn (no `stroke-dashoffset` animation) and just sharpens. `OP_MIN_VISIBLE`/`OP_REVEAL_MS` retune **together** so the ~2.5s resolve can't be cut off mid-sharpen by the readiness gate (a fast load must never dissolve mid-blur). Ambient depth/vignette layers open *underneath* the resolve (≤2.5s), not as a distinct first motion.
- **Center on the WORDMARK's optical center, not the group box** *(v3 "too low" fix)*. The lockup is bottom-weighted (the arch is a thin crown; the wordmark carries the mass), so centering the group's bounding box always sat the eye low. `OP_GROUP_CENTER` (0.46) now positions the **wordmark's own center** at 46% of the visible viewport; arch and tagline are satellites derived from it at a **locked 2:1 spacing** (arch↔wordmark gap = 2× wordmark↔tagline gap, true visible edge-to-edge, in wordmark-heights — kept as `2×` so the ratio can't drift when the base is tuned). The orphaned `op-bloom` horizon seam was removed entirely (it was the OurBanner gradient idiom bleeding in). Foot = a **typeset "VELAYO INC." line, no glyph** (the full Velayo lockup is a hero asset — illegible small, and its crest doubles the crown).
- **A fixed full-screen overlay above a taller-than-viewport body must lock `document.body` scroll for its lifecycle** *(new cross-cutting pattern; the splash shake fix, `5be6f0a`)*. The splash's own `.op-splash { overflow:hidden }` already clips its children, so a scrollbar appearing during the splash could only be the **document behind** it: the app body is taller than the viewport, and its vertical scrollbar toggling as content loads reflows the full-width overlay sideways (~15px = a visible horizontal shake). Fix = set `body.style.overflow = "hidden"` on mount, restore the prior value on unmount. This is NOT a global `overflow-x` mask (which would hide a genuinely-overflowing element) — the overlay legitimately shouldn't let the body scroll behind it. Applies to any future full-screen fixed overlay.
- **Dismissal is readiness-gated, not a timer.** `onDone` fires on intro-minimum-elapsed **AND** `!loading` (the household/provisions load flag, in scope), ~2s minimum + ~5s failsafe. **Cold-start only** (`showSplash` state, never re-arms within a mount). `prefers-reduced-motion` collapses the whole thing to a plain fade.
- **Position everything relative to the WORDMARK, never the viewport.** The arch, horizon line, and tagline all derive from the wordmark's **measured bounding rect** — measure the transform-free WRAPPER (stable during the reveal) for the box, `offsetWidth` for the untransformed width. The cluster then composes as ONE group centered on the **visible** viewport: `window.visualViewport.height`, NOT the layout viewport a `position:fixed` overlay is sized to (taller on mobile → reads high). Re-measure on resize / orientation / `visualViewport` resize / font load. **The bug-catching test is resizing window HEIGHT** — anything viewport-anchored drifts or collapses; every positioning bug this build hit (arch creep toward the caps, horizon line on the descenders, top-heavy composition) was viewport-anchored. Gotcha: the wordmark is Playfair *italic* — descenders hang lower/further-right than upright metrics suggest, so a baseline-relative offset that looks right can still collide; clear it with a font-size fraction below the measured box.
- **The wordmark hand-off measures its target at runtime — and HIDES it.** On the dissolve the splash wordmark (a positioned clone) travels to the **actual header title element's** `getBoundingClientRect()` + font-size (that element has a ref) and **holds at full opacity**. Crucially the **real header title is hidden** (opacity 0, but still laid out so it stays measurable) **until the clone unmounts**, then revealed in the SAME React commit (`showSplash → false`) — clone-removed and title-shown land in one frame = an invisible swap. Miss either half and it breaks: if the target isn't hidden, both render (double wordmark); if the clone crossfades out before the reveal, there's a gap. Fallback when unmeasurable (e.g. wordmark hidden over a photo): a clean fade — never a visibly-misaligned landing. Verify at 390px & 430px — **on the phone, the verification device for the entry** (not a post-desktop confirmation).
- **The dissolve is a simple surfacing** — no water wash on the entry: the espresso scene fades to reveal the cream body + espresso header beneath while the wordmark lands on the header. The wordmark **emerges in place** (opacity + blur, no translation) so the hand-off is the sequence's ONLY travel. Header standardized to always render "*Our*Provisions" so the hand-off lands on the same words. Footer V-mark still wants a **true transparent** SVG/alpha PNG (the current knocked-out PNG reads cool against Dune).

### In-flight guard on an async action button *(2026-07-10 — `src/App.js`)*
Any button whose `onClick` awaits a mutating RPC must be disabled for the duration of the await, or a second tap in the window fires a duplicate. Pattern: a dedicated boolean state (e.g. `creatingInFlight`) raised BEFORE the await and cleared in `finally` (so an error re-enables it), driving `disabled` + a dimmed style + an "…ing" label, PLUS an early-return `if (flag) return;` guard closing the tiny window between the first tap's state commit and React re-rendering the `disabled` attribute — "belt for the eye, suspenders for the race." Same family as `deliberateLossRef`. First shipped as the duplicate-household-creation fix (`565b133`): the Create button was un-disabled during a ~2s-on-3G `create_household`, so a 259ms double-tap made two households. Applies to every create/submit affordance. Note: a disabled button does NOT stop a *code-path* re-fire (retry hook) — that needs server idempotency; button-disable is only for the human double-tap. Two supporting facts: **`create_household` (migration 006) is a bare single-INSERT** — no retry, no upsert, no idempotency — so a double-invoke yields two distinct ids, each with its own owner membership (guard is currently client-side only). And **`get_my_households` returns one row per membership** (joins `household_members → households`), which makes a switcher dupe *decidable as a data dupe, not a render bug*: count distinct household ids vs. count memberships (the diagnostic that landed the duplicate-create root cause).

### Invite flow — Web Share + lazy-generate on intent *(2026-07-10 — `src/App.js`)*
The invite is the Beta 1 activation pivot, and the depth metric counts *sends*, not copies — so the flow must actually send. **Send** via `navigator.share` (feature-detected — branch on its existence, never UA-sniff; Copy is the fallback and the sole action where Web Share is absent, e.g. most desktop). **Message is a single source of truth** (`INVITE_MESSAGE(householdName, url)`) used by both the on-screen preview and the `navigator.share` `text`, so preview === what's sent; copy echoes the welcome-email "bring your first mate" vocabulary. **Lazy-generate (Option B):** do NOT write a `household_invites` row on panel open. `prepareInvite()` runs on the first intent signal — a ~500ms idle-after-open timer (cleared on unmount, so a fast open/close writes no row) OR an explicit Send/Copy tap (which awaits the returned url rather than assuming state is set). `prepareInvite` is idempotent (guards on `inviteUrl`/`invitePreparing`, raises before the await, clears in `finally` — the in-flight-guard family) so the timer and a tap can't double-write. All invite state resets on panel close AND on active-household change (a link is scoped to the household it was minted for). **Edge note:** iOS Safari restricts `clipboard.writeText` to a direct user-gesture context, so a *cold* Copy tap (no idle pre-generate yet) that awaits before writing may fail silently — mitigated because the idle timer normally has `inviteUrl` ready by tap time; fall back to selecting the readonly field if it ever bites.

### Referral attribution rides the invite seam *(2026-07-16 — specced, not built; per `docs/specs/active/SPEC_referral_primitive.md`)*
Referral attribution reuses the join seam rather than adding a parallel one. `bootstrap_new_user` (SECURITY DEFINER) already accepts `p_invite_code` and joins atomically; referral takes `p_ref_code` the same way — code → `users.id` → `users.referred_by`, in one transaction. ⚠️ This is a **signature change to the hot path for every signup**, so the **no-ref case (both codes null) is the regression guard** — verify an organic signup still bootstraps cleanly before shipping. The metric is the column itself: `count(*) where referred_by = <id>` — a `users` row only exists if the person cleared Clerk *and* bootstrapped in, so it counts arrivals, not ghost Clerk accounts. Do NOT add a sends table or a counter: a `navigator.share` send is unobservable (the OS reports nothing), and intent (the tap) overcounts every cancel. Attribution and measurement are the same row.

### sessionStorage survives the Clerk redirect *(2026-07-16 — pattern; `pending_invite_code` live, `pending_ref_code` specced)*
Clerk strips URL params for brand-new users, so any link-borne code must be captured at app entry and read back after bootstrap, then **cleared regardless of outcome** — a code that has been *attempted* must not re-trigger on a future visit. `pending_invite_code` already proves the pattern; `pending_ref_code` mirrors it exactly. `users.referral_code` itself is set by **trigger at user creation** (not lazy-generated — a code is an attribute, not an artifact, so the `household_invites` junk-row rationale for lazy generation does not apply); it reuses the proven `household_invites` code generator/format (e.g. `DE39W9`) — do not invent a second format — and requires a backfill for existing rows.

### Deliberate-loss guard — a watchdog defers to a user-initiated state transition *(2026-07-09 — `src/contexts/ActiveHouseholdContext.js` + `src/App.js`)*
The durable pattern for "a background watchdog poll must not race a deliberate state transition." A `deliberateLossRef` is raised at the START of any user-initiated household loss (delete/leave), *before* the destructive RPC, and cleared in the handler's `finally`. The `checkPresence` watchdog bails while it is set, so the poll cannot double-fire a removal notice the deliberate path is already handling. Two independent handlers reacting to one event is the race surface: `handleDeleteHousehold`/`handleLeaveHousehold` and the poll both call `resolveAfterHouseholdLoss`; the fix makes the poll *defer* to the deliberate path rather than trying to detect intent after the fact (the abandoned `selfDeparture` approach — now dead scaffolding). Guard the *whole* action from before its first async boundary, self-clearing via `finally` so a thrown RPC can't wedge the watchdog off permanently. `resolvingRef` is retained as an inner guard for resolver re-entrancy and resolver-internal awaits. **The false "No longer a member" P0 was this class of bug:** v1 guarded only the resolver's lifetime, leaving the ~2s-on-3G RPC window unguarded; v2 raised the guard to the handler layer. External removals are unaffected — no deliberate handler runs, the flag stays false, the poll fires normally (regression-verified).

### Removal-notice household name comes from the pre-update list *(2026-07-09 — `src/contexts/ActiveHouseholdContext.js`)*
When `checkPresence` detects the active household vanished, it captures that household's name from `myHouseholdsRef.current` (which still holds the departed household at detection time) BEFORE overwriting the ref, and threads it through `resolveAfterHouseholdLoss`'s optional `lostName` param into the notice. Previously the notice used the sticky `activeHouseholdNameRef`, which could hold a stale prior name (showed "Madbury" for a deleted "Test House 101"). Complements the sticky-resolved-value ref pattern — the sticky ref remains the fallback when no `lostName` is supplied.

### Session replay (Splunk RUM) — unmasked + rendering, usable as a diagnostic instrument *(2026-07-09 — `src/rum.js`)*
Splunk RUM session replay is now unmasked and rendering; it surfaced the blank-catalog bug this session. ### Outage triage — the hypothesis-killing diagnostic sequence *(2026-07-15 — no code)*
The sequence that localized the prod outage, each step **killing** a hypothesis rather than gathering support for a favored one:

2. **Observability → error codes** — a **522** (Cloudflare→origin timeout), uniform across every Data API endpoint (`get_my_households`, `bootstrap_new_user`, `catalog_items`) — not a Postgres 5xx.

4. **Dev/prod comparison on identical code** — the highest-value single fact. Dev healthy eliminated every explanation living in the repo and localized the fault to the prod instance → platform-layer restart.

### `CatalogItemRow` render invariant — Add XOR stepper, never a stepper at qty 0 *(2026-07-10 — `src/App.js`)*
A catalog row renders **EITHER** an "Add" ghost pill (qty 0) **OR** the −/N/+ stepper (qty > 0) — never both, never a stepper reading 0. The two are mutually exclusive by design: **on-list ⇔ qty > 0 ⇔ stepper; not-on-list ⇔ qty 0 ⇔ "Add".** Tapping Add calls `onUpdateQty(name, 1, …)`; − at qty 1 calls `onUpdateQty(name, 0, …)` → the existing `updateQty` removal path (`Math.max(0, qty)`, `qty <= 0` removes) → re-render → qty 0 → "Add" pill (snap-back is automatic, no extra logic). Because zero is never rendered, the ambiguous zero-state is structurally gone. **Any future feature must preserve this mutual exclusivity** — never render the stepper at qty 0, never render "Add" at qty > 0. Add and stepper share one ghost-pill treatment (transparent-on-cream, clay-lo `#C9A97A` outline) so the two states read as one control family.

### Touch-state pattern — guard `:hover` behind `@media (hover: hover)` + blur on tap *(2026-07-10 — cross-cutting, `src/App.js`)*
Interactive controls that **re-render under the touch point** must guard their `:hover` styling behind `@media (hover: hover)` and blur on tap, or mobile Safari (WebKit) latches a sticky hover/focus fill after the touch sequence. **iOS = WebKit for every browser**, so the iPhone is the source of truth for touch-state bugs. Keep `:active` **unconditional** (it's the legitimate press feedback on touch); move only the `:hover` fill inside the media query; and call `e.currentTarget.blur()` in the `onClick` so no focus state lingers on a freshly re-rendered element. First shipped as the Add-button sticky-hover fix (`dea88a1`): repro was tap Add → +/− to 0 → touch another row, landing the held `:hover` on a re-rendered Add pill.

### `scrollbar-gutter: stable` on `html` — the vertical scrollbar must not be allowed to appear mid-load *(2026-08-10 — APP-WIDE, `src/index.css`)*
**The startup "shimmy" is the page's vertical scrollbar arriving late, not anything that is animating.** Device-observed sequence: the view paints with **no** vertical scrollbar → content finishes loading → the page crosses the **viewport-height threshold** → Chrome adds the scrollbar → the **~15px** it occupies **narrows the viewport** → the centered column slides **~7px left**. Fix is one line, `html { scrollbar-gutter: stable; }`, which reserves the space **from first paint** so nothing shifts.

**This is app-wide, not a Browse concern.** *Any* view whose content crosses the viewport-height threshold during load shows the identical shift — Plan and Shop included. **Desktop-only in effect:** mobile overlay scrollbars occupy no layout space, so there is nothing to reserve and nothing to fix there.

> **Diagnostic lesson, recorded because it cost real work:** the shift is horizontal, small, and lands during load, so it gets **misattributed to whatever happens to be moving at the time**. It was blamed on the Browse rail's first-run nudge, and removing the nudge did not fix it — because the nudge was never the cause. **When something shifts sideways during load, suspect the scrollbar before suspecting the animation.**

Related, and **not** to be re-derived as the fix: the splash locks `document.body.style.overflow` while it is mounted (`SplashScreen`, `src/App.js`). That was an earlier, **splash-scoped** workaround for this same mechanism — and its *restore* on unmount used to be precisely the moment the scrollbar appeared. The gutter now handles the scrollbar globally; the lock stays only for its independent reason (**no scrolling behind a full-screen overlay**).

### Measuring a horizontal rail must wait on `document.fonts.ready`, not just on the pill set *(2026-08-10 — cross-cutting, `src/App.js`)*
**Emoji metrics settle AFTER the elements exist.** A rail whose children carry emoji reaches its final `scrollWidth` some time after the child set stops changing, so any effect keyed only on "the pills are here" measures a width that is about to change. **Key rail measurement on the pill set *and* re-measure on `document.fonts.ready`** — `if (document.fonts?.ready) document.fonts.ready.then(measure).catch(() => {})`.

Recorded because it bit the **same feature three times** in one build: the `scrollLeft: 0` resting-position pin (parked the rail mid-list with Staples off-screen), the pager buttons' overflow measurement (gated on a stale width), and the first-run nudge (overflow test ran before the true width existed). A fourth consumer will arrive; it needs the same guard.

Two adjacent scroll-snap traps in the same container:
- **A snap container that gains children re-runs snap selection** — which is why the resting position is pinned *explicitly* rather than left alone. Pills arrive asynchronously (catalog load, emoji metrics), and each arrival can re-park the rail mid-list.
- **`scroll-snap-align: start` snaps to the *snapport*, which includes the scroller's padding area.** Without a matching `scroll-padding-left`, a container's `padding-left` is visually cancelled at rest and the first child parks flush to the edge. This surfaced as two symptoms — "missing padding" and "clipped edge mask" — that were one bug seen from both ends. The current rail sidesteps it by carrying **no horizontal padding at all**, so the content box *is* the content column and the first pill's snap offset is 0.

### Browse carries TWO filter types, and `selectedCategories` alone is blind to one *(2026-08-10 — `src/App.js`)*
**Category values** (`catalog_items.category` — open set, mandatory 📦 fallback) and the **Staples predicate** (`household_staples` row-presence per migration 016 — *not* a category value; `catalog_items.is_staple` is a dormant rollback column with no live read path by design). They narrow in two layers: **Layer 1 applies the Staples predicate, Layer 2 narrows by category.**

### Deliberate exception to the `@media (hover: hover)` convention — and why it currently has no live instance *(2026-08-10 — `src/App.js`)*
The touch-state pattern above requires `:hover` be gated behind `@media (hover: hover)`. The Browse rail's desktop scroll affordances **deliberately deviated**: `hover: hover` is false on the hybrid hardware those controls exist to serve, so guarding would have disabled the feedback on precisely the devices needing it. Accepted cost was a cosmetic stuck hover after a tap.

**Recorded as reasoning, not as live code** — the pager buttons carrying this exception were removed the same day in favour of a styled scrollbar, so the convention currently has **no live exception**. Kept because the next hybrid-hardware affordance will face the identical trade-off. Companion principle from the same controls, also now without a live instance: **the visible affordance and the touch target are different objects** — the pagers kept a full-height `<button>` hit target with a smaller visible chip inside, rather than shrinking the button down to the chip.

### Styled scrollbars — Chromium ignores `::-webkit-scrollbar` if `scrollbar-width`/`scrollbar-color` is set *(2026-08-10 — cross-cutting, `src/App.js`)*
**Setting `scrollbar-width` or `scrollbar-color` on an element makes Chromium discard that element's `::-webkit-scrollbar` rules entirely.** The two syntaxes cannot coexist on one selector: the standard property wins and the styled track silently reverts to the browser default. Declare the webkit rules bare and put the Firefox fallback behind `@supports not selector(::-webkit-scrollbar) { … }`, which only a non-webkit engine passes. **A tidy-up that flattens the two into a plain `scrollbar-width: thin` will kill the styled track in Chrome and produce no error** — the CSS still parses.

Companion fact, device-confirmed on a **Surface (touchscreen + attached mouse): `hover`, `pointer`, `any-hover` and `any-pointer` all report false.** **Never gate a mouse affordance on a pointer media query** — on hybrid hardware it hides the control from exactly the mice that need it, and hybrid hardware is common, not an edge case. Gate on a **measurable layout fact** (overflow) or on **viewport width**, which media queries answer honestly. Scrollbars need no gate at all: mobile browsers use transient overlay scrollbars, so a styled `::-webkit-scrollbar` renders on desktop and effectively nothing on touch.

### hiddenIdsRef poll guard *(June 9)*

### pendingCheckRef — optimistic-check poll guard *(2026-07-13 — `src/hooks/useProvisions.js`)*
The exact twin of the `pendingQtyRef` quantity guard, for `checked` state. ### getTokenRef stable-ref pattern *(June 9)*

List state on a hot 2s poll (`loadListItems` via `get_list_items_for_household` RPC); catalog on a cooler 20s poll (`refreshCatalog` via `refreshCatalogRef`). ### Guarded catalog merge *(June 12)*
`refreshCatalog` computes `next`, does a field-level diff (id, category, is_staple, price_hint) against `catalogRef.current`, and only commits (`setCatalogMap` + ref update) when something actually changed. ### Durable-intent over one-shot side effects — invite-join `pendingJoinId` *(2026-07-01 — `src/App.js`)*

**Cross-cutting pattern.** Where an action's *trigger* is consumed on the very load that carries it — a stripped URL param, a single-use invite/token, a cleared `sessionStorage` flag — the resulting state change must NOT be a one-shot that depends on that load completing uninterrupted. Hold the **intent** in React state and reconcile it reactively against the authoritative source when it arrives.

First applied to invite-join activation. The auto-switch into a joined household was an inline one-shot: `bootstrap_new_user` strips `?invite=` and the invite is single-use, so the `just_joined_household*` flags exist only on the consuming load. It survived reload only because `switchHousehold` writes `localStorage.activeHouseholdId`; if that write was interrupted (slow `refreshHouseholds`, mid-flight reload, membership guard rejecting on a slow network), the flags were already stripped and the invite spent, so the next context-init re-pinned the prior household with no recovery. First fix (`1c5a916`): when the join flags are read, store `joinedId` as `pendingJoinId` state; a `[pendingJoinId, myHouseholds]` effect fires `switchHousehold(pendingJoinId)` (then clears it) once `myHouseholds` contains that id. Preserves the single-writer invariant below — the switch still routes through `switchHousehold`, never `setHousehold`.

> **REFINEMENT (2026-07-01, prod correction — reopened; `docs/specs/built/SPEC_join_activates_household_ADDENDUM_reopen.md`):** durable intent is necessary but **not sufficient**. The first `pendingJoinId` fix moved intent into React state but still reconciled **single-fire** against `myHouseholds` — it switched only when the joined id was *already* present. On prod, membership propagates into `get_my_households` **late**: `myHouseholds` did not yet contain the joined household when the effect evaluated, the effect did not re-fire when it finally arrived, and both `pendingJoinId` and the sessionStorage flag stranded (reproduced on prod: `just_joined_household_id` SET but never consumed, `activeHouseholdId` still on the prior household). Corrected form: (1) treat the surviving `sessionStorage` flag as the durable source of "unfinished join intent" and re-derive `pendingJoinId` from it, not a single `[loading, household]` fire; (2) re-fire the reconciling switch on **every** change of the authoritative source (`myHouseholds`) while the intent is unresolved; (3) clear the durable marker **only after the target state is confirmed** (`activeHouseholdId === joinedId`), never on the attempt. Optionally, a bounded `refreshHouseholds()` retry to pull late membership in. The general rule: a reconcile that consumes durable intent must be *retriable against a late-arriving source*, and the marker cleared on confirmation, not on the attempt — else a source that populates late is missed and the intent strands.

> **Prod-vs-dev latency is a first-class test variable for timing-dependent fixes.** The first join fix passed three dev runs and failed the first prod run because prod membership propagation is slower. Reconcile races, propagation waits, and realtime convergence are NOT certified by dev-green — they require prod verification. Recorded so future sessions don't repeat the dev-green→prod-fail miss.

> **Confirmed on deployed dev (2026-07-01), not from the migration file:** `bootstrap_new_user` returns `joined_via_invite=true` for an existing user accepting a valid, unconsumed invite — the invite branch takes priority and does NOT short-circuit for established users. Verified by observing a fresh-invite consuming load auto-switch a multi-household user into the joined household, resolving the standing CLAUDE.md caution that the SQL editor may hold a stale function version. The join-activation defect was therefore purely client-side; the RPC was not touched.

**The lens is the single writer.** `ActiveHouseholdContext` is the sole authority on the active household. Any join path — Route A (`?invite=` via bootstrap) or a future wired paste-a-code UI — lands the active household through `switchHousehold`, never by calling `setHousehold` directly. The dead `acceptInvite` in `useProvisions` (which swaps its own `household` state directly and would leave `activeHouseholdId` stale) is the anti-pattern this invariant pre-empts: wiring it as-is would create a split-brain where `household` and `activeHouseholdId` disagree.

### classifyFetchError + ConnectivityPill — offline/retry handling *(Jun 20)*

Transport-layer failures (no HTTP response) are classified separately from real HTTP errors, RLS denials, and Supabase error codes so the app can degrade gracefully without alarming the user.

- **`src/lib/classifyFetchError.js`** — pure function (no imports). Returns `'transient'` for: message includes "Failed to fetch", "NetworkError", "ERR_CONNECTION", "ERR_NETWORK", "ERR_INTERNET_DISCONNECTED", "ERR_NAME_NOT_RESOLVED"; `name === 'AbortError'`; `name === 'TypeError'` with message matching `/fetch|network/i`. Returns `'real'` for everything else. **Default is `'real'`** (fail safe — a loud real error surfacing is better than silently swallowing one).
- **`src/contexts/ConnectivityContext.js`** — state machine. `connState` starts `'online'`. `reportTransientFailure()`: if online or recovered → `'reconnecting'`; after 3 consecutive calls → `'offline'`. `reportSuccess()`: if reconnecting or offline → `'recovered'` + starts 2s timer → `'online'`; timer cleared on re-entry to prevent stacking. `failureCount` is a ref (UI doesn't need to render from it); `connState` is state. `ConnectivityProvider` wraps the tree outside `ActiveHouseholdProvider`. `useConnectivity()` hook.
- **`src/components/ConnectivityPill.js`** — returns `null` when `connState === 'online'`. Three visible states: *Reconnecting* (sand `#EFE2CC`, amber `#B8860B` pulsing dot, 1.3s ease-in-out opacity+scale); *Offline* (`#F0E0BE`, steady dark dot, "showing last saved"); *Back online* (teal `#CDEDE8`, teal dot). Fixed bottom-center (`bottom: 28px`, mirrors toast), `pointerEvents: none`, `role=status aria-live=polite`.
- **Read-path pattern:** catch block calls `classifyFetchError(err)`. Transient → `reportTransientFailure()`; keep last-good data; return without `setError`. Real → existing `setError(...)` unchanged. `reportSuccess()` called on boot load success and 20s catalog-poll success. Applied to: catalog-refresh ×2, `loadListItems`, household-fetch in `loadForHousehold`.
- **Write-path pattern:** rollback is **unconditional** (runs on any catch — transient AND real). Then branch: transient → `reportTransientFailure()`, real → `setError(...)`. `reportSuccess()` after server confirms the write. Applied to: `updateQty`, `toggleChecked`.

### Two-effect hook pattern *(established Jun 17 — `src/hooks/useProvisions.js`)*

`useProvisions` uses a deliberate two-effect split to separate identity setup from household-scoped data loading:

- **Effect 1** (deps: `userId, clerkId, email`): creates the Supabase client once (guarded by `if (!supabaseRef.current)` against GoTrueClient stacking), runs `bootstrap_new_user`, stores the fallback household id and internal user id into refs, then sets `bootstrapped` STATE to `true`. **Deps key on IDENTITY only (2026-06-29):** `fullName` was removed — it is a cosmetic attribute that only feeds `bootstrap_new_user`'s `p_full_name` (a no-op for existing users). Including it meant a display-name edit (which writes Clerk → changes `fullName`) re-fired full session bootstrap, calling `setLoading(true)` with no matching clear (the success-path `setLoading(false)` is owned by Effect 2, which did not re-run), wedging the app on "LOADING YOUR PROVISIONS…". Session-bootstrap effects must depend on identity, never cosmetic state.
- **Effect 2** (deps: `activeHouseholdId, userId, clerkId, bootstrapped`): resolves the target household by trusting `activeHouseholdId` unconditionally (already set to the joined household on auto-switch via `switchHousehold`, unchanged on silent join); falls back to bootstrap fallback only when context is empty (fresh device / pre-restore). `justJoinedViaInviteRef` is still set from bootstrap but is no longer read in the resolver. Effect 2 runs all household-scoped loads + polls, and on teardown clears intervals + resets per-household state (`listRows`, `quantities`, `checked`, etc.).

**Critical invariant:** the cross-effect handoff gate MUST be a STATE value (`bootstrapped`), not a ref. A ref change cannot re-trigger Effect 2. If Effect 2 runs before bootstrap finishes (which is intermittent), it returns early — and if only a ref is set, nothing re-fires. Using state ensures React re-runs Effect 2 the moment bootstrap completes. The `cancelled` flag in Effect 2 cleanup prevents stale async writes after a household switch mid-flight.

### Client-side reconciliation effects — Effect 1b (`full_name` from Clerk) *(2026-07-01 — `src/hooks/useProvisions.js`)*

**Cross-cutting pattern:** Clerk-sourced user attributes that bootstrap cannot reliably capture must be reconciled by their own idempotent effect, decoupled from bootstrap. `bootstrap_new_user` writes such attributes at most once, at the worst possible time (Clerk's `firstName`/`lastName` often arrive *after* the initial session), is a no-op on later sessions, and — critically — cannot take `fullName` as a dep without reintroducing the loading-wedge (see Two-effect pattern). So an attribute written only by bootstrap is written once, too early, and never reconciled.

**Effect 1b** is the reference implementation for `users.full_name`:
- **Own effect**, deps `[fullName, bootstrapped]` — re-evaluates once bootstrap finishes and again whenever Clerk's name arrives/changes.
- **Guards:** body no-ops unless `bootstrappedRef.current` && `internalUserIdRef.current` are set and the trimmed name is non-empty.
- **`lastSyncedNameRef`** prevents a write loop / repeated no-op writes; a reads-before-writes check skips the update when the stored value already equals the incoming name (avoids needless realtime churn).
- **Reuses the RLS-proven write path** (`db.from("users").update({ full_name }).eq("id", internalUserIdRef.current)` — the same update `updateFullName` runs, which RLS already permits for a user's own row). **Never calls `bootstrap_new_user`**, sidestepping its 4-overload ambiguity entirely.
- **Non-fatal:** on error it logs and returns — attribution degrades to the email-prefix fallback, never blocks the app.
- **MUST stay decoupled from the bootstrap effect** — coupling reintroduces the `fullName` loading-wedge the Effect 1 dep-list warns about.
- **Self-heal, no backfill:** existing NULL `full_name` rows repopulate the next time each user opens the app with a Clerk name present. Do not hand-write names into `users`.

### Household-scoped UI state resets on active-household change *(2026-06-29 — `src/App.js`)*

Any UI state that *describes a specific household* must be cleared when the active household changes, or it goes stale and contradicts the new context. Three such surfaces were found and fixed this session; the class is systemic (elevated to a next-session audit). Because creating a new household auto-switches active context, a single reset keyed on the active household covers BOTH the switch and create-new paths — no separate create handling needed.

- **Invite-link reset:** `useEffect(() => { setInviteUrl(null); setInviteCopied(false); }, [household?.id])`. ### Membership-presence polling — realtime fallback when RLS suppresses soft-delete events *(Jun 22)*

When Supabase realtime cannot deliver a soft-delete event to the affected user (because the SELECT policy filters `deleted_at is null` and the new row image fails that check), poll instead.

- **Interval:** 30s, keyed only on `clerkId` in the effect dep array — all household state read via refs to avoid stale closures.
- **Guard:** `error || !data` — holds position only on genuine transient failures (error truthy or null data). A successful empty result (`{error:null, data:[]}`) is a legitimate removal signal (user was removed from their only household) and is allowed through to the auto-provision branch. A `data.length === 0` clause was deliberately removed when it was found to suppress valid auto-provision on the only-household path. Confirmed safe: PostgREST never returns `{error:null, data:[]}` on a network failure — those always surface as `error` truthy or `data` null.
- **In-flight guard:** any create-on-detect action (auto-provision `create_household`) uses a ref flag to prevent duplicate spawns on double-fire.
- **Disambiguation:** the deliberate-loss guard (`deliberateLossRef`, raised by `handleDeleteHousehold`/`handleLeaveHousehold` before their RPC and cleared in `finally`) makes the poll defer to a user-initiated leave/delete rather than firing a removal notice for it; a forced external removal has no deliberate handler running, so the poll fires normally. See the "Deliberate-loss guard" Key Pattern.
- **General rule:** any future realtime-on-soft-delete feature using an `is_member_of`-style policy will hit the same RLS suppression — use this polling pattern as the fallback.

### Sticky-resolved-value ref pattern *(Jun 24 — `activeHouseholdNameRef` in `ActiveHouseholdContext.js`)*

When a ref value can be clobbered by a background mutation (e.g. `myHouseholdsRef` is overwritten by `refreshHouseholds` before `checkPresence` reads it), use a sticky ref that only updates when the value can be *positively resolved*:

```js
const activeHouseholdNameRef = useRef(null);
const resolved = myHouseholds.find((h) => h.id === activeHouseholdId)?.name;
if (resolved) activeHouseholdNameRef.current = resolved; // skip update when unresolvable
```

The sticky ref updates on every render where the active household is still in `myHouseholds`. After `refreshHouseholds` drops the departed household from the list, subsequent renders find `resolved = undefined` and skip the update — the ref **retains the last known correct name**. A belt-and-suspenders `??` fallback inside the consumer (`nameForNotice = activeHouseholdNameRef.current ?? oldListLookup`) provides "never worse than today" guarantees. This pattern applies to any mutable-ref value that can be pre-clobber by a concurrent async mutation before the interval reads it.

### Function body verification via pg_proc.prosrc *(Jun 20)*

The Supabase dashboard SQL editor auto-appends `limit 100`, which silently breaks scalar-returning calls like `pg_get_functiondef('fn'::regprocedure)` with a misleading parse error. Reliable verification path: query `pg_proc.prosrc` with a position check:

```sql
SELECT proname, position('ON CONFLICT' in prosrc) > 0 AS upsert_present
FROM pg_proc WHERE proname = 'insert_list_item';
```

Returns a clean boolean, immune to the auto-limit. Use this pattern over `pg_get_functiondef` whenever you need to confirm a function body change was saved. (Extends the existing "SQL Editor may silently keep old versions" caution in CLAUDE.md.)

### Header layering principle *(established 2026-06-28 — `SPEC_household_indicator.md`)*

The app shell has two distinct chrome layers with different rendering scopes:

- **Outer chrome** (avatar row, active-household indicator, kebab menu): App-level. Always rendered whenever the user is signed in. Survives household switches — it wraps them. Correct home for identity signals and cross-household navigation.
- **Inner chrome** (title bar, wordmark, action buttons, SHOP/BROWSE/PROFILE tabs): Household-context layer. Rendered inside the active-household scope. Reflects the current household's state (member count, wordmark singular/plural).

Design rule: any chrome element that must remain stable across household switches belongs in the outer layer. Any element that reflects the *current* household's state belongs in the inner layer. Mixing them (e.g. household name in the title bar) creates a flash-of-old-name on switch. The active-household indicator (Phase I) lives in the outer layer for this reason.

### Cascade integrity check — probe prod before migration apply *(established 2026-06-28)*

Before applying any migration that adds a column (or any other additive schema change) to a table that exists on prod:

1. Run a live column-existence query against the **prod SQL editor tab** (not dev, not docs, not memory):
   ```sql
   SELECT column_name FROM information_schema.columns
   WHERE table_schema='public' AND table_name='<table>' AND column_name='<column>';
   ```
2. Confirm the result is empty (column does not yet exist) before issuing the `ALTER TABLE`.
3. After apply, verify via `pg_proc.prosrc` (for RPCs) or a schema query (for columns).

This pattern caught a potential `shopping_sessions.deleted_at` double-add on 2026-06-28 — the prod table already had the column (from an earlier untracked apply), which would have caused the `ALTER TABLE` to fail with a duplicate-column error if issued without checking first. **Never trust docs or session logs as prod-state authority.** The DB is the source of truth.

### Dev-environment hygiene — multi-user removal testing *(established Jun 25)*

Junk household accumulation and lookalike `+testN` accounts invalidate test signals. Before any multi-user removal/membership test:

1. **Read-only inventory first.** Run queries mapping live users → live memberships → households (all joins filtered `deleted_at IS NULL`). Establish DB ground truth before touching anything.
2. **Keep-list + reversible soft-delete.** Declare which accounts/households to keep; `SET deleted_at = now()` on everything outside the list. Never hard-delete test artifacts — they remain recoverable.
3. **Build fresh fixtures via the real invite flow.** Create `+testN` accounts using the actual invite-join path, not SQL inserts. Invite-first guarantees the account is single-household with no personal My Household — the clean point-4 fixture.

Root cause of four consecutive false signals before this discipline: two accounts both showed "My Household" in the switcher (lookalike aliases), and the observed window was a non-member account.

### Insert-only / no-SELECT RLS pattern *(established 2026-07-05 — `beta_signups`)*
First table accepting writes from unauthenticated (anon) users. The `rls_auto_enable` event trigger locks it on creation. Grant the `anon` role one INSERT policy with `with check (true)` and **deliberately NO SELECT, UPDATE, or DELETE policy**. The absence of a SELECT policy is the security model: a visitor can write a row but can never read one back, protecting founder-only operational columns (`status`, `fit_note`) from visitor reads. ### Telemetry must never block the user *(pattern — 2026-07-16 — landing-page arrival mechanic)*
The `beta_signups` insert is **fire-and-forget**: the redirect to Clerk fires regardless of the insert's success. Never trap someone at the door because a telemetry table hiccuped. Generalizes to any future analytics / mission-control write that sits on a user's path — the write is a side effect of the journey, never a gate on it.

### Ask, don't parse *(pattern — 2026-07-16 — landing-page form)*
The signup form collects first and last name **separately** so no name is ever split on whitespace ("Mary Jo Kelly" → Mary / Jo Kelly). `beta_signups.name` stores them joined; the Clerk pre-fill URL params carry the split. Same pixels, opposite emotion: a filled *uneditable* field feels like surveillance; a filled *editable* one feels like service. Consequence: `beta_signups.email` may diverge from the eventual Clerk email — accepted, and the concrete reason real gating (RPC + Clerk hook keyed on email) would be fragile.

### Cross-origin surface — `ourprovisions.app` → Supabase Data API *(2026-07-16 — new, not yet live)*
The static landing page (`ourprovisions.app`, Cloudflare DNS → Vercel, **grey cloud not orange** or TLS loops) fetches the Supabase Data API from a **different origin** than the app. **CORS must allow `ourprovisions.app`** — a new requirement that **fails silently in a way that looks like a code bug**. First cross-origin Supabase caller in the system.

### iOS install coach-mark pattern *(established 2026-07-06 — `SPEC_pwa_install_coachmark.md`)*
Detection gate: iOS + Safari + `navigator.standalone === false` + localStorage dismissal-count < 2. Two-step dismissal ladder: first open shows the coach-mark; next fresh open re-offers with softer "last call" copy; second dismiss → never again. "Visit" = fresh app open (distinguishes opens from background resume). Counter persisted in localStorage — per-device by design; clearing data or using a new device re-offers, which is correct for a home-screen nudge. Android untouched — Chrome's native Add-to-Home-Screen prompt handles it. Goal: remove Dan from the install loop on both platforms.

### New-user cold-start gate *(established 2026-07-06 — `SPEC_new_user_coldstart.md`)*
A timed walk must prove before the signup email flips to self-serve: (1) a zero-state Clerk identity creates a household without confusion, (2) adds a first item that persists, (3) Realtime behaves for a solo brand-new household, and (4) the first screen is a warm empty-state — not a void. Cold-start is a test-and-fix cycle, not a feature build. Full self-serve "come aboard" link is honest only once a true zero-state user is verified to onboard cleanly; until green, the email stays personal.

### Three-Repo Separation Principle
`velayo-os` (how the company runs) / `velayo-platform` (product infra shipped into apps) / app repos (the fleet). The OS never ships to a customer and is never a production dependency. Cockpit ≠ engine.

### Design Principles
- **Narrative layer vs. environment layer split on different clocks.** The session log (narrative) can stay unified long after repos/deploys/access (environment) must separate. Don't let "keep it simple" creep from the log layer into the deploy layer.
- **No secrets on the dashboard.** The Harbour lists doors (links), never contents; targets are independently auth-gated so "leaked = low stakes" stays true.

### Known Gotcha — Cloudflare Access
Access gates a *hostname*, not a Worker — sibling routes (`workers.dev`, preview URLs) aren't covered by the custom-domain app. The standalone Access app must be explicitly **Created** (not just policy-saved), or the door stays open. Hit this live: first incognito test loaded through because the app was unsaved.

### Secret-Handling Confirmation (OurProvisions)
`.env`/`.env.local` hold only publishable/anon keys (Supabase anon, Clerk `pk_`), correctly gitignored. No `service_role`/`sk_` secrets in client files. RLS is the real lock, not key-hiding. **Superseded in detail 2026-08-09 by "Secrets & Credentials" above** — which adds the human/machine split, the agent distribution model, and the caveat that "RLS is the real lock" is only true while RLS is actually on (it is off on three tables).

### Growth sub-fleet: the Content Loop *(chartered 2026-08-15)*

A four-role content pipeline that mines Velayo's own docs for teaching moments:
**Content_Idea → Copy Drafter → Editor → Publisher**. Copy Drafter is the existing
Growth charter with its remit extended; the other three are new. Two human gates
instantiate the Growth group's standing rule — *no Growth agent addresses a human
unsupervised: draft, never send*. **Publisher is the only role that ever sends,** and
only immediately downstream of the final gate. The gate queue is unified but tagged
`[scope]` + `[owner]`, defaulting to Dan — the Harbour's lane-ownership pattern
applied one level down, so adding a second human later is a value change, not a
redesign.

- **Silence is the default, expected output.** Three consecutive "nothing found"
  passes is a correct result, not a failure — and it is what makes eventual
  Agent-tier promotion low-risk.
- **Content_Idea triggers only on SESSION END, never on a schedule.** The docs it
  reads only change at SESSION END; a timer would re-check an unchanged door, and
  would introduce the fleet's first timer-based compute dependency before it is
  proven necessary.
- **Two signal sources, not one stretched across channels.** DECISIONS LOG →
  blog + LinkedIn. ROADMAP DONE stamps + ExD-tagged entries → Instagram.
- **Publisher is the cadence-keeper.** Per-channel ceilings (blog ≤30d, LinkedIn
  ≤10d, Instagram ≤3d) are **maximums, never floors**; an empty backlog means it
  skips silently rather than manufacturing a post.

> Role naming: **`Content_Idea`** was called "Watcher" during design and renamed
> 2026-08-15 — it sat one letter from Ops' **Watchman**, a different role in a
> different group. Watchman is unchanged.

### Pattern: charter vs. instance separation for agent pipelines

A **charter** (role definitions, gates, rules) is project-agnostic and written once.
An **instance** is that charter parameterized by source docs (input) and publish
channel (output), scoped to one project — each with its own Content_Idea paired to
that project's own SESSION END, because `project_knowledge_search` is project-scoped.
**Role names stay fixed across instances**; no per-app renaming. Velayo OS is the
active instance, OurProvisions next, OurKeep gated behind beta exit per standing rule.

### Build constraint: watchers stand alone from day one

**Every Agent candidate is built as a standalone watcher with its own read access
from day one — never grafted on as a step inside a Seat's script**, even while still
human-triggered. A grafted watcher fails the independent-observation-surface
condition *structurally*, and no amount of later scheduling repairs it; it would need
a rewrite. Built standalone, promotion is a **config change** — remove the keystroke
gate — and nothing else moves.

### SmartList — the shared-artifact collaboration primitive *(NAMED 2026-08-19 — **[Velayo OS] scope, NOT OurProvisions-specific**)*

**Velayo's shared-artifact collaboration primitive, first instantiated by OurProvisions.** This is the intended **reuse surface** for any future fleet app carrying a shared list-like construct — inherited, **not rebuilt from scratch each time.**

**Two orthogonal axes:**

- **Axis 1 — Relevance (signal vs. noise). Per person, binary. ALREADY SHIPPING — not hypothetical.** *"Hide is a lens, not an edit"* **is** this axis: one shared item exists **once**, with its integrity intact, and each person locally suppresses what is noise **to them** without touching what is still signal **for someone else.**
- **Axis 2 — Intensity ("I care about it" vs. "I care about it *often*"). A gradient, not a toggle. NOT yet unified as a concept.** It exists today only as disconnected partial instances: **ingredient Staples** (`household_staples`, migration 016) and the **meal-cadence** discovery logged in `ROADMAP.md`'s idea log on 2026-08-19.

> ⚠️ **NAMING — do not conflate this with "consumption signal."** The consumption-signal frame is **household vs. market** (intention + receipts as sensors on what a household actually consumes), set out in full in **`docs/strategy/STRATEGY_consumption_signal.md`** and summarised in this document under § Meals / Provisioning IA. **SmartList's axes are INTERPERSONAL** — inside one shared artifact, between the people using it. **Same word, different concept; keep them separate in the docs.**
